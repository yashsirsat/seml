# Detailed Bus Tracking System Report

## 1 Introduction

### 1.1 Background
The MSRTC Bus Tracking & Booking System is a full-stack web application built with Flask (Python) for real-time bus location tracking, seat booking, station management, and timetable viewing. Tailored for Maharashtra State Road Transport Corporation (MSRTC), it uses CSV data (msrtc_bus_data_sample.csv), geolocation (reverse_geocoder, Nominatim), email notifications (flask-mail), and session management.

### 1.2 Problem Statement
Passengers face uncertainty with bus locations/arrivals, manual bookings, no live updates. Station masters lack easy location sharing. Solution: Real-time API-driven tracking, in-memory booking, bot automation.

### 1.3 Objectives
- Responsive UI for tracking/booking/auth.
- REST APIs for location/buses.
- Role-based access (station_master).
- Email confirmations.
- JS polling for live updates.
- Local deployment with public tunnel ready.

## 2 Frontend Development

### 2.1 UI/UX Design
Jinja2 templates extend base.html with style.css for responsive design. Key pages:
- **home.html**: Dashboard with role-based links (Track, Book, Timetable, Station Master).
- **signin.html/signup.html**: Authentication forms with validation (alphanumeric password >=8 chars).
- **track.html**: Bus selection dropdowns + live location display (JS polling /bus_location_api).
- **booking.html**: Bus filter → seat map (2+2+3 sleeper layout, 43 seats) → seat selection → payment.
- **payment.html**: Confirmation + auto email via flask-mail.
- **timetable.html**: Filterable bus schedule table from CSV.
- **station_master.html**: Role-restricted bus location manual update (lat,lon input) + auto-bot activation list with stop buttons.

Responsive CSS grid/flexbox, MSRTC-themed styling.

## 2.2 JavaScript Features
- Auto-refresh polling for live bus locations (every 5-10s on track.html via /bus_location_api).
- Dynamic seat map highlighting (booked/available seats).
- Form validation + AJAX submissions.

## 3 Backend Development

### 3.1 Flask Application Structure
Single-file Flask app (app.py ~500 LOC) with Blueprint-free MVC pattern:
- **Routes**: / (redirect signin), /signup, /signin, /logout, /home, /station_master (POST role-protected), /track, /booking (multi-step), /payment (email), /timetable.
- **APIs**: 
  - GET /bus_location_api?bus_name=...&bus_type=...&bus_start_time=...: Returns {lat, lon, location, timestamp}.
  - POST /api/auto_update_location: Bot-called, updates location.
  - GET /api/get_started_buses: List active buses.
  - GET /api/stop_sharing/<bus_key>: Deactivate auto-tracking.

### 3.2 Core Logic
- **Auth**: In-memory users dict, session-based, role checks (station_master only for location updates).
- **Booking Flow**: Filter buses from CSV → Select → Interactive seat map (get_seat_map(): 43 seats 2+2+3) → In-memory bookings dict → Payment + flask-mail Gmail SMTP confirmation.
- **Location Services**: Manual input (lat,lon) → Nominatim API (street-level) fallback reverse_geocoder (offline country-level).
- **State Management**: Global dicts (users, bookings, bus_locations keyed by "bus_name_type_start_time", started_buses set).

### 3.3 Dependencies Integration
Flask-Mail (Gmail app password), Requests (Nominatim), Reverse_geocoder (offline geo).

## 4 Data Management & Storage

### 4.1 Data Sources
- **Primary Dataset**: `msrtc_bus_data_sample.csv` (25+ entries):
  | Column | Description | Sample |
  |--------|-------------|--------|
  | bus_name | e.g. "Shivneri Express", "MSRTC Local" | Shivneri Express |
  | bus_type | AC/Non-AC | AC |
  | start_point/end_point | Routes | Pune/Mumbai |
  | station_place | Stops | "Pune, Nigdi, Pimpri..." |
  | bus_start_time | Schedule | "06:00 AM" |

  Used for dropdown filters, timetable, unique bus keys (`{bus_name}_{bus_type}_{bus_start_time}`).

### 4.2 In-Memory Storage
- `users`: Dict {email: {name, password, role}}.
- `bookings`: Dict {bus_key: set(seat_numbers)}.
- `bus_locations`: Dict {bus_key: (lat, lon, location_name, timestamp)}.
- `started_buses`: Set of active bus_keys for bot tracking.
- **Limitations**: Session-persistent only (restart clears), suitable for demo. Future: SQLite/Redis.

### 4.3 Utility Functions
- `get_unique_bus_data()`: Parses CSV for dropdown options.
- `get_location_name((lat,lon))`: Hybrid geocoding (Nominatim fallback reverse_geocoder).
- `get_seat_map()`: Returns 10x7 grid (43 seats, sleeper layout).

## 5 Bots & Automation

### 5.1 Auto Station Master Bot
`api/auto_station_master_bot.py` – Standalone Python script for real-time GPS simulation:
- **Flow**: Loads CSV buses → Loop (60s): Poll /api/get_started_buses → For active: Get current loc → Add GPS drift (±100m) → POST /api/auto_update_location.
- **Integration**: Triggered manually via station_master.html → Adds to started_buses → Bot activates auto-polling → Stop via /api/stop_sharing/<key>.
- **Features**: Random drift simulates movement, default Pune coords fallback.
- **Run**: `python api/auto_station_master_bot.py` (parallel to `python app.py`).

### 5.2 Selenium Bot
`api/selenium_bot.py` – Likely for web scraping (timetables/locations), integration pending (from TODO_bot.md).

**Deployment**: Terminal1: `python app.py` | Terminal2: `python api/auto_station_master_bot.py` for live tracking.

**Vercel Deployment** (Frontend + Serverless Backend):
- Install Vercel CLI: `npm i -g vercel`
- Create `vercel.json` (see below).
- `vercel login && vercel --prod`
- Frontend (static/templates) served directly, backend as serverless functions.
- Bots: Deploy separately (e.g., Railway/Render) or use Vercel Cron.

## 6 System Architecture

### 6.1 High-Level Design
MVC pattern:
- **Model**: CSV data, in-memory dicts.
- **View**: Jinja2 templates + CSS/JS.
- **Controller**: Flask routes/APIs.

**Components**:
```
Station Master UI → Manual Update → bus_locations + started_buses
                    ↓
             Auto Bot ←→ APIs (poll/update)
                    ↓
Live Track UI ← JS Poll ← bus_location_api
```

## 8 Testing & Deployment

### 8.1 Local Testing
1. `pip install -r requirements.txt`
2. Terminal 1: `python app.py` (runs on http://127.0.0.1:5000)
3. Terminal 2: `python api/auto_station_master_bot.py` (auto-tracking)
4. Browser: Signup (station_master role) → Station Master: Update location → Track: Live polling → Book seats → Payment/email.

**Verification**:
- Role access enforced.
- Location updates/geocoding accurate.
- Booking conflicts prevented.
- Email delivery (check spam).
- Bot drift/movement visible on track page.

### 8.2 Production Deployment (Vercel)
**Vercel Setup** (Primary Deployment):
1. Add `vercel.json`:
```
{
  "version": 2,
  "builds": [
    { "src": "app.py", "use": "@vercel/python" }
  ],
  "routes": [
    { "src": "/(.*)", "dest": "app.py" }
  ]
}
```
2. `vercel --prod` → Deploys to https://your-project.vercel.app
3. Update Gmail app password in env vars (VERCEL env).
4. Static assets auto-handled.

**Alternative**: Ngrok for local tunnel, Gunicorn+Nginx for VPS.
- DB: PostgreSQL/Redis (Supabase/Upstash).
- Bots: Supervisor/Celery or separate service.
- CI/CD: GitHub Actions → Vercel.

**Verification**:
- Access Vercel URL: Signup → Station Master → Activate bot → Track live.
- Emails via Vercel env.
